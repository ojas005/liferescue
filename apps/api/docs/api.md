# LifeRescue API (platform contract 0.1.0)

Spec of record: [`packages/contract/openapi.yaml`](../../../packages/contract/openapi.yaml) (frozen by LR 03, generated
from `contract.api_models`). [`../openapi.json`](../openapi.json) is what this app serves at `/openapi.json` (disabled when
`LIFERESCUE_ENV` is production/prod/staging; also generated by `python scripts/export_openapi.py`, drift-tested).
`tests/test_contract_conformance.py` asserts every contract path/operation/response model exists in the served spec.

Base URL (local): `http://localhost:8000`. JSON only. Every response carries `X-Request-ID` and
`X-Content-Type-Options: nosniff` / `Cache-Control: no-store`. Request bodies over 64 KiB -> 413 `payload_too_large`.

**Identity (PLACEHOLDER, no authentication - contract assumption):** a single demo user. Optionally send
`X-Actor-Id: <id>` (`[A-Za-z0-9_.@:-]{1,128}`); it defaults to `demo-user` and is only recorded as `decided_by` / audit actor.

| Operation | Method + path | Success | Errors |
|---|---|---|---|
| `health` | `GET /api/health` | 200 `HealthResponse` `{status, contract_version, model_adapter}` | |
| `listWorkflows` | `GET /api/workflows` | 200 `[WorkflowSummary]` | |
| `createRun` | `POST /api/runs` `{workflow_id, input, workflow_version?}` | 201 `RunResponse` | 404 `workflow_not_found`, 422 `invalid_input` |

## Errors

All non-2xx bodies are the contract `ErrorResponse`: `{"error": "<stable code>", "message": "<safe text>"}`. Messages
never echo submitted values, SQL or exception text. Mapping (contract `ERROR_CODES`): `workflow_not_found`,
`run_not_found`, `approval_not_found` -> 404; `illegal_transition`, `guard_failed`, `approval_invalid`,
`concurrent_modification` -> 409; `invalid_input` -> 422 (also request-validation errors).
Additions NOT in the contract `ERROR_CODES` (PROPOSED ASSUMPTION - REQUIRES HUMAN APPROVAL): `payload_too_large` (413),
`internal_error` (500), `not_ready` (503 from `/readyz` only).

## Run lifecycle (contract state machine)

`INTENT -> EVIDENCE -> RESEARCH -> PLAN -> POLICY -> APPROVAL -> ACTION -> VERIFICATION -> COMPLETED`; terminal:
`COMPLETED | FAILED | DENIED | CANCELLED`. Poll `/timeline?after_seq=<next_seq>` until `terminal == true`. This API
persists and serves the run; advancing it is the run engine (LR 06). Until `app.runtime.wiring.build_engine(ports)`
exists, `app/placeholder_engine.py` only creates the run at `INTENT` (cancel works). `tests/dev_app.py` runs the full
pipeline with the contract `ReferenceRunEngine` over the real SQL stores for development.

## Approvals

`POST .../approvals/{approval_id}`: unknown approval or one belonging to another run -> 404. Approvals expire after 900 s
(lazy, on read/decide) and are bound to a payload digest; an expired, already-consumed or digest-mismatched approval
cannot authorise an action. Repeating the *same* decision returns the snapshot unchanged (idempotent, SECURITY T5); the
opposite decision -> 409 `approval_invalid`. Approve: run proceeds; deny: run -> `DENIED`.

## Timeline payload redaction

Every event payload is redacted at write time and reduced to an allowlist of keys per event type
(`app/db/event_policy.py`); unexpected keys are dropped (names recorded in `_dropped`), real-tool output is reduced to
key names. See PR-DESCRIPTION.md for the SECURITY-REQUIREMENTS ids (P1, K3, ...).

Stored payload keys per event `type` (anything else is dropped; the engine owner must request additions, LR 04 + LR 08 review):

| type | allowed payload keys |
|---|---|
| `state_change` | `from`, `note`, `reason`, `to` |
| `intent` | `adapter`, `category`, `entities`, `model`, `summary`, `urgency` |
| `evidence` | `collected`, `missing` |
| `research` | `queries`, `result_count`, `skipped`, `source_urls` |
| `plan` | `steps`, `summary` |
| `policy` | `action_digest`, `outcome`, `policy_version`, `reason`, `risk`, `rule_id`, `step_id`, `tool` |
| `approval` | `action_digest`, `approval_id`, `decided_by`, `expires_at`, `status`, `step_id`, `summary` |
| `action` | `action_digest`, `error`, `mocked`, `output`, `simulated`, `status`, `step_id`, `tool` |
| `verification` | `checks`, `passed` |
| `audit` | `audit_records`, `chain_head_before_summary` |
| `error` | `code`, `reason` |

`TimelinePage.terminal` is true only when the run is terminal and no more events remain; poll with `after_seq=next_seq`.
Simulated writes are labelled by the contract (`mocked: true` on results and `action` events) - the UI must show SIMULATED (T6).

## Audit

`audit_log` is append-only (no UPDATE/DELETE/TRUNCATE; triggers + least-privilege role) with a SHA-256
`prev_hash`/`hash` chain (PROPOSED ASSUMPTION per contract). No HTTP endpoint exposes it in 0.1.0.
